# M10.5.3 同会话多轮与消息队列契约

2026-10-17，已完成本片本地验收，见../testing/M10.5.3-validation.md。继承M5、M10.5.1/.2恢复、脱敏、独占及工作区绑定约束。

同一taskId/sessionId追加多轮SDK事件；后续message或supplement各有独立requestId，目录只存其SHA256及原文摘要hash，内容先脱敏持久化。新提交不伪装成独立会话。SDK公共入口记录输入与user.message及实际Loop turn.started的关联，prepared envelope仍可从原日志前缀重建。Loop不依赖Web实现。

每会话最多8条待执行消息、256条后续受理记录（独立资源配额）；每页32条。补充指令排入FIFO，明确在当前完整轮次关闭SDK/清理后的下一轮边界应用，不修改已发送模型请求、已批准工具参数或权限。不提供本片范围外的模型协议/结构化提问。

目录采用Web版本3，版本2在独占下备份并追加激活标记；旧宿主拒写，SDK协议1.9与JSONL格式1保持。受理先持久化队列，再在执行前写工作区占用指针和started事实，最后构造SDK；丢响应只能GET核对，不能自动重新POST。队列取消只取消未启动项，不撤销既有副作用。进行中取消不自动运行后续队列。

宿主重启后未开始队列为PAUSED，需操作者明确开始；已started未完整结算为UNKNOWN，沿原离线核实规则处理，核实不自动续跑。正常/强制退出均不能以恢复自动执行旧消息。运行/UNKNOWN绑定跨catalog及工作区别名保持。恢复继续前核对未归档、SDK ready、原工作区无其他写者；每轮配置由可信宿主选择并记录，不改写旧快照。

草稿仅当前页面内存，含秘密的内容不进入localStorage/sessionStorage；刷新/关闭会丢弃未发送草稿，脏草稿阻止意外导航。浏览器仅存无内容的提交ID用于刷新后GET核对；已持久受理消息保留于脱敏事实，未确认消息不声称取消或未执行。

验收矩阵：真实SDK同会话至少3轮与前缀重建；忙碌排队/补充、8条边界、排队取消、双击和多标签竞争、刷新及受理响应丢失不重复；宿主退出后无自动执行；UNKNOWN及归档阻塞；恢复显式启动；故障checkpoint不进入模型，原目录迁移/工作区占用保持；真实Java宿主Chrome和既有全回归使用同一最终JAR/UI。实际337项Java、16项客户端及Chrome多轮15项/既有回归已通过，证据见M10.5.3-validation.md。

接口：GET/POST /v1/tasks/{id}/turns；GET以offset（32条页）或request（原requestId）核对，POST正文为requestId/text/kind。start/cancel使用受理结果中的submissionId（SHA256）作为路径字段，正文为空对象；返回task及submission，后者含状态、输入序号、实际turnId和待执行内容的脱敏200字符预览。取消/结束后投影不保留正文，原追加事实仍保留。全局受理ID冲突拒绝，不跨会话复用；冷核对扫描逐条释放目录事实，不无限驻留。单SDK日志32MiB/10000事件及费用/步骤/时长限制继续生效，可能先于256条配额触发。

待核对期间锁定输入、方式和丢弃操作，核对不覆盖新稿；设置/导航继承草稿保护。跨轮次只保持原读取流程，不因队列更新反复建立SSE；后台更新保持用户向上阅读位置，主动发送/开始才恢复跟随。

2026-10-22 R2 增补：当前持久化、SDK 自包含输入/初始化、问答暂存与最终持久解析、容量及平台边界以 [R2 补充契约](OCR-R2-contracts-2026-10-22.md) 为准；旧 `userEventId` 分离输入仍兼容读取，新输入正文与关联同一事实发布。最终实测见 [R2 修复记录](OCR-R2-remediation-2026-10-22.md)，不将本条契约说明算作验收通过。
