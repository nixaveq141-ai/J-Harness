# M10.5.9 根因核对与最小诊断

## 已证明：WebKit 导航诊断不等于未捕获 Promise

检查 Api.readJson/stream 的 reader.cancel 拒绝均已有 catch；Questions.read 的 API 拒绝也有 catch。这是静态检查，不能单独证明浏览器行为。

新增可直接运行的 `frontend/tests/diagnostics/webkit-navigation.mjs`，仅启动无头 WebKit，不含 React 或产品业务代码，不计入271个验收用例。三个受控场景一次执行：

1. 导航取消已经存在的同源 JSON 读取：catch 收到 Load failed，没有 pageerror。
2. 目的页面延迟500ms提交；beforeunload 后25ms仅发起一次已捕获的同源读取：两次拒绝均被 catch，仍出现同样的 access control checks pageerror，且 DOM error/unhandledrejection 都为零；现有精确导航分类命中。
3. 真正抛出未捕获异常：DOM error 和 Playwright pageerror 均可观察，按对应事件等待，不靠 sleep 猜事件顺序。

最小探针先前只取消已有读取未复现；加导航开始后的单次读取即复现。第一版对照还存在两个通道先后顺序的断言错误，已改成事件等待；失败日志保留。最终三场景通过：`.build-cache/M10.5.9/webkit-navigation-cause-final.log`。

源码链条：[WebKit ThreadableLoader::logError](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/loader/ThreadableLoader.cpp) 直接调用 `addConsoleMessage(MessageSource::JS, MessageLevel::Error, ...)`；[Playwright WebKit _onConsoleMessage](https://github.com/microsoft/playwright/blob/main/packages/playwright-core/src/server/webkit/wkPage.ts) 将该来源/级别转换为 pageerror。本机已安装1.62.1代码也逐行核对。因此不能从此 pageerror 推断产品存在未捕获 Promise，也不能将所有同文字错误一概豁免；仍只识别明确导航窗口内旧文档观察到的精确只读 URL，其他错误继续失败。

## 已证明：原生诊断丢失原因，不代表原生故障已修复

SystemCredentials.invoke 在新实例 supported=false 时抛 HarnessException(CREDENTIAL_STORE_UNAVAILABLE)，旧探针只分类 IOException，于是将该明确原因写成 PROBE_FAILED。现在从 HarnessException.code 读取白名单代码，增加已有 worker 中断/失败及响应限额/格式固定分类；清理失败也保留安全原因。未知代码/消息仍固定 PROBE_FAILED，绝不输出原生错误文本或凭据。

扩展原有 `nativeProbeReportsOnlyFixedSafeFailureCategories`，验证异常类型差异、秘密消息/秘密未知代码及固定分类，单项通过（未访问真实密钥库）。这只修复证据缺口；第15轮的历史 PROBE_FAILED 没有原始原因，不能事后认定它就是 STORE_UNAVAILABLE。

## 独立缺口：命令根 Process 结算

命令 Tree 原只看 ProcessHandle，未像终端/MCP清理一样等待所拥有的 Process 状态。确定性替身让句柄已退出而根 Process 仍存活：旧策略失败；补充根状态后，延迟结算通过，持续存活仍报告 residual/UNKNOWN，原两秒清理预算未延长。相关41项通过，新增一个身份，契约为650/106，原649身份全部保留；尚未执行650完整验收。

这不是 Windows 目录占用的已证实根因。[OpenJDK21 Windows ProcessImpl](https://github.com/openjdk/jdk21u/blob/master/src/java.base/windows/native/libjava/ProcessImpl_md.c) 和 [ProcessHandleImpl](https://github.com/openjdk/jdk21u/blob/master/src/java.base/windows/native/libjava/ProcessHandleImpl_win.c) 都通过 GetExitCodeProcess 检查活跃状态，不能套用 POSIX reaper 缓存解释 Windows 故障。

## 未决：第17轮 Windows 临时目录锁

40053162601 的 macOS/Linux 完整通过，Windows `cancellationKillsObservedRealChildTreeAndPreservesHonestScope` 方法全部断言通过，JUnit 随后删除临时根失败（仅根被占用）；原 ZIP ae64dc12787fb4200768dfedf8599d06dd236f1ab8bcf17804cadc9674fd787d 保留。没有锁拥有者证据，不能认定产品、扫描器或 runner 的哪一个负责。

该场景现把命令 CWD 放进独立空子目录，PID/就绪清单留在外层；原结果断言后立即尝试删除精确 CWD，一次失败即报告 tracked/residual 并保留失败，不重试删除。托管 Windows 专项准备微软签名的 [Sysinternals Handle](https://learn.microsoft.com/en-us/sysinternals/downloads/handle)，仅在这次删除失败时查询此目录的拥有者，不关闭任何句柄。此改变使失败尽量发生在证据仍存在时，而不是晚到 JUnit 回收阶段才得到“其他进程占用”。本机该单项通过。

两个进程夹具将100/200ms固定启动 sleep 替换为现有 ProcessProbe 就绪清单，不放宽产品预算或原结果断言。进程专项改为手动，防止推送自动制造新测试轮次。后续只需一次有诊断的相关41项三平台验证；没有新原因证据前不启动第18轮全量。
