# 执行诊断、权限与离线核实

选择已结束的任务，时间线上方自动展示失败/拒绝/取消/超时及待核实摘要。耗时、命令请求期限、主体是否启动、可能影响和清理证据来自原事件；没有记录即未知。工具包装器进入并不等于命令启动。SHELL_REQUIRED 通常是将 Shell/批处理放进 ARGV：先检查参数，确需 Shell 时显式指定 CMD/POWERSHELL/SH 并走原有审批，页面不会自动替你改模式。

设置 → 权限：default 使用已有策略，读取可执行，写入/普通命令逐次审批，精确可信命令例外；read-only 拒绝非只读工具（含命令执行）。保存仅影响后续新任务；运行/UNKNOWN时拒绝保存，旧任务保留 config.selected 快照。回答问题、批准计划与批准工具是三种不同动作。

“结果待核实”不是成功，也不是可以直接重试：命令可能已执行、部分修改已落地，或模型请求/工具/终端尚未结算。环境关闭成功、observedClean=true 或空 residualPids 不能证明任务成功或所有进程已停止。

展开“打开安全核实向导”，下载脱敏的离线交接JSON。文件仅包含读取时的事实及操作清单，不执行命令、不追加核实、不清除状态。新事实可能使旧交接过时，维护前须重新 inspect。

1. 在原启动窗口输入 `:quit` 停止旧宿主及相关执行者；确认没有仍在执行的模型/工具/子任务。不以独占锁代替实际检查。
2. 检查实际工作区文件、进程、外部服务与影响；不要按旧PID杀进程，不凭口头确认填结果。
3. 在原工作区运行 CLI `sessions inspect --session TASK_ID`（完整入口例如 `java -jar harness-cli/target/harness-cli-0.1.0-SNAPSHOT.jar --workspace WORKSPACE sessions inspect --session TASK_ID`）。这是只读检查。
4. 根据实际未决类别和原始关联，使用已有 `verify --call ... --outcome APPLIED|NOT_APPLIED|PARTIAL`、`sessions verify-request --event ...`、`verify-terminal`、`verify-environment`、`verify-subagent`。完整参数见 CLI `--help` 和 M5/M7/M8 契约。理由必须记录具体检查证据；不提供一键清空模板。
5. 底层SDK未决事实处理后，使用 `sessions verify-web --session TASK_ID --web-catalog CATALOG_ID --reason ...` 核实目录。相同根/绑定及独占catalog/session维护锁、底层Recovery检查仍必需。重新启动后只读取；任何后续执行都由操作者另行决定。

旧记录可能没有配置快照或bodyEntered字段；界面不会补造。Web诊断schemaVersion=1为只读增量，SDK协议1.9、JSONL格式1不变。M10.5.2之后的会话、多轮等能力不由本片提供。
